# CLAUDE.md - WDS (Windows Development System)

## Project Overview

WDS is a set of Dynace classes that make developing Windows GUI applications easy using C (not C++). It wraps the Win32 API in an object-oriented layer via Dynace (an OO extension to C). Built on top of Dynace at `../Dynace`. Used commercially for ~15 years.

**Current status:** Builds and runs as a 64-bit application under Wine on Linux
(Fedora 42, GCC 15, Wine 10.x). Native Windows build (MSVC/NMAKE) is untested
but should be unaffected — all Wine-specific changes are conditionally compiled.
Dynace (the underlying system) is current and works fine.

- Source: https://github.com/blakemcbride/WDS
- Dynace: https://github.com/blakemcbride/Dynace (`../Dynace` relative to this repo)

## Languages & Key Technology

- **Primary:** C with Dynace OO preprocessor (`.d` files → `.c` files via `dpp`)
- **Integrations:** Java (bidirectional), ODBC/SQL, OLE, Scheme/MzScheme
- **Build:** GNU Make (Linux/Unix), NMAKE (Windows), mk (Plan 9)

## Build Instructions

### Prerequisites
- Dynace built and installed at `../Dynace` (configured in `makefile.inc`)
- WINE development headers (for Linux/macOS builds with `WINE=1`)

### Linux/Unix (with WINE)
```bash
make setup.unx     # Line ending conversion
make makegens      # Generate generics.h via DPP
make                # Build all (WINE=1 is set in makefile.inc)
make DEBUG=1        # Debug build
```

### Windows (NMAKE)
```bash
nmake -f makefile.msc all          # Full build
nmake -f makefile.msc makegens     # Generate generics.h
nmake -f makefile.msc all-scratch  # Clean rebuild
```

### Build Output
- Libraries go to `lib/wds.a` (Unix) or `.lib` (Windows)
- DPP converts `.d` → `.c`, then `gcc`/`winegcc` compiles to object files

## Key Build Configuration (`makefile.inc`)

- `DYNACE_PATH` - Path to Dynace installation
- `WINE=1` - Enable WINE support (set by default)
- `DEBUG=1` - Debug build (`-g` instead of `-O`)
- `DPP` - Dynace preprocessor path
- `DPPOPTS = -C` - DPP options

## Dynace OO Model & Conventions

### File Types
- `.d` files: Dynace class definitions (preprocessed by `dpp` into `.c`)
- `.iv` files: Intermediate generated files
- `generics.h` / `generics.c`: Auto-generated by DPP, define all generic functions

### Class Structure
```c
defclass ClassName {
 class:              // Class (static) variables
    HINSTANCE cInstance;
 instance:           // Instance variables
    HANDLE    iHandle;
    object    iParent;
 init: class_init;   // Class initialization method
};
```

### Naming Conventions
- `g` prefix: Generic functions with fixed args (compile-time checked) — e.g., `gProcessMessages()`
- `v` prefix: Generic functions with variable args (runtime dispatched) — e.g., `vNew()`, `vPrintf()`
- `m` prefix: Macros wrapping generic calls — e.g., `mLoadMenu()`, `mAssociate()`
- All methods/variables in `.d` files are private; public API is via generics only
- One class per `.d` file

### Memory Management
- Automatic garbage collection (mark & sweep or Boehm GC with `BOEHM_GC` flag)
- `gDispose()` for explicit deallocation when needed

### Entry Point
GUI applications use `start()` (not `main()`):
```c
int start()
{
    object win = vNew(MainWindow, "Title");
    return gProcessMessages(win);
}
```

Core (non-GUI) programs use standard `main()` with `InitDynace(&argc)`.

## Architecture

```
Application Code
    ↓
Generic Functions (public C interface)
    ↓
Private Methods (dispatched by Dynace type system)
    ↓
Win32 API / WINE / ODBC / OLE
    ↓
OS / Database
```

**Key classes:** Application.d, Window.d (7834 lines), Dialog.d, Control.d, Database.d, Statement.d

## Testing

No automated test framework. Examples in `examples/` and `WinExam/` serve as de facto acceptance tests — build and run manually. Each example has a `readme` file.
