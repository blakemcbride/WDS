@chapter Mechanics

This chapter, in concert with the WDS examples, describes the tools and
actual steps necessary to create WDS application programs.  The best
method of learning is to go through the example programs located under
the @code{WinExam} directory in the order in which they appear.

@section Build Methods
There are two supported build methods for WDS applications:

@itemize @bullet
@item
@strong{Linux/macOS:} GNU Make with GCC/winegcc (via Wine).
@item
@strong{Windows:} NMAKE with Microsoft Visual C++ (MSVC).
@end itemize

Both methods are command-line based.  WDS builds as a native 64-bit
application on both platforms.

@section Build Environment Setup

@subsection Linux / macOS (Wine)
The following must be in place before building:

@enumerate
@item
Install Wine and the Wine development headers (e.g.@: @code{wine-devel}
on Fedora, @code{libwine-dev} on Debian/Ubuntu).
@item
Build Dynace (a separate package).
See @code{https://github.com/blakemcbride/Dynace}.
@item
Edit the file @code{makefile.inc} in the WDS root directory and set
@code{DYNACE_PATH} to point to your Dynace installation directory.
Verify @code{WINEINCPATH} is correct (default is
@code{/usr/include/wine}).
@end enumerate

@subsection Windows (MSVC)
The following must be in place before building:

@enumerate
@item
Install Visual Studio with C/C++ command-line tools.
@item
Build Dynace (a separate package).
See @code{https://github.com/blakemcbride/Dynace}.
@item
Edit the file @code{setupenv.bat} in the WDS root directory and set
@code{DYNACE_PATH} to point to your Dynace installation directory.
@item
Run @code{setupenv.bat} from a Visual Studio Developer Command Prompt.
@end enumerate


@section Building WDS From Scratch
The procedure used to build WDS from scratch is fully described
in @code{docs/BUILD.txt}.  A brief summary follows.

@subsection Linux / macOS
From the WDS root directory:
@example
make makegens
make
@end example

@subsection Windows
From the WDS root directory (in a Developer Command Prompt after
running @code{setupenv.bat}):
@example
nmake -f makefile.msc makegens
nmake -f makefile.msc all-scratch
@end example

New users will want to read all the files in the @code{docs} directory.


@section Examples Setup

@subsection Linux / macOS
Each example directory contains a GNU @code{makefile}.  Simply
@code{cd} into the example directory and run @code{make}.

@subsection Windows
The Windows NMAKE makefiles (@code{makefile.msc}) are not installed in
the example directories by default.  To install them, run the following
from the @code{WinExam\setup} directory:

@example
windows
@end example

This copies the appropriate @code{makefile.msc} into each example
directory.  You can then build any example with:

@example
nmake -f makefile.msc
@end example

The @code{WinExam\setup} directory also contains:

@table @asis
@item clean
Deletes build artifacts from all example directories.

@item cleanxx
Removes the installed @code{makefile.msc} files from all example
directories (returns to as-shipped state).
@end table




@section Example Files
This section documents the files which are contained in each example
program.

@table @asis
@item readme
This file describes the purpose of the example.  It should be read
first.

@item main.c
This file is the complete source code to the example program.

@item main.txt
This is a fully commented version of @code{main.c}.  It describes all
aspects of the current example which are unique.

@item main.rc
This is the resource script describing the resources used by the
application.  It is created and edited via a resource editor.

@item resource.h
This file is created by the resource editor.  It is used by the
application code to associate resources defined in @code{main.rc} to
macro names.

@item makefile
GNU makefile for building under Linux/macOS (Wine).

@item makefile.msc
NMAKE makefile for building under Windows (MSVC).  Installed by
running @code{WinExam\setup\windows} (see Examples Setup above).

@end table


Once an application is built, the only file needed to run it is
@code{main} (Linux) or @code{main.exe} (Windows).



@section Building The Examples
To build an example under Linux/macOS, @code{cd} into the example
directory and run:

@example
make
@end example

To build a debug version:

@example
make DEBUG=1
@end example

To build an example under Windows, @code{cd} into the example
directory and run:

@example
nmake -f makefile.msc
@end example



@section Debugging
Due to the fact that WDS is the first thing which Windows sees
when it executes an application and the fact that WDS is not normally
built with debugging information, the following procedure will make it
easier to debug your application code.

First compile your application with debugging information.  Then when you
wish to debug the application, set a break point at ``start''.  You
can then debug your application by telling the debugger to run to the first
break point.  You will then see the initial function of your application
and may debug as usual from that point.

Since WDS comes with full source code, you may compile it
with debugging information and debug through the WDS code
as well as your application specific code.


@section Building Your Own Application
The best method of building your own application would be to start
with one of the example programs and proceed from there.  This way
all the compiler, linker and other options will be preset.  

If you plan to create your own Dynace classes along with your WDS
application, it would be best for you to start with the WDS example
which illustrates the creation of a Dynace class along with the WDS
application.  This example has the appropriate make file logic to
handle custom classes along with a WDS application.

@section DPP
@code{DPP} is the pre-processor used by Dynace to convert class definition
files into C source files.  It is also used to generate generic files
and perform generic/method argument checking.  This utility is only needed
when creating new classes and is only used by more advanced WDS users
who wish to create their own Dynace classes.

This utility is fully documented in the Dynace language manual.
